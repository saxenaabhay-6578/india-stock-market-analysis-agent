# India Stock Market Analysis Agent

## 1. Overview

This is a Python pipeline that, for a fixed universe of 20 NIFTY-50 stocks,
pulls recent market data, computes technical indicators, asks Claude to turn
those indicators into a structured multi-horizon price prediction, stores
every prediction immutably in SQLite, later scores older predictions against
real outcomes, and reports all of it in an Excel workbook generated from the
SQLite database of record.

This is **Phase 1**: manual execution only (no scheduled/automated run yet),
a static universe, and a single free market-data provider. Real fundamentals
data, real news/sentiment data, paid data providers, and automated scheduling
are explicitly deferred to a later phase.

**Disclaimer.** Every generated Excel report carries this exact text (from
`src/reporting/excel_report.py::DISCLAIMER`), and it applies to everything in
this repository as well:

> This report is generated by an automated technical-analysis tool for
> research and educational purposes only. It is NOT investment advice. Past
> accuracy does not guarantee future performance. Consult a registered
> investment advisor before making financial decisions.

```bash
pip install -r requirements.txt
cp .env.example .env
# then edit .env and set:
#   ANTHROPIC_API_KEY=sk-ant-...
```

`config/settings.py` holds **only** non-secret paths and tunables — `DB_PATH`,
`REPORTS_DIR`, `LOGS_DIR`, `TOP_N`, `MARKET_DATA_LOOKBACK_DAYS`,
`MARKET_DATA_MAX_RETRIES`, `MARKET_DATA_BACKOFF_SECONDS`, `CLAUDE_MODEL`,
`PROMPT_VERSION`. It **must never contain a key or any other secret**. The
Anthropic API key lives only in the git-ignored `.env` file and is read
directly from the environment by the Anthropic SDK (via `anthropic.Anthropic()`
after `dotenv.load_dotenv()` in `src/run_daily.py`) — it never passes through
`config/settings.py`.

## 4. How to run

```bash
python -m src.run_daily
# Full Top-20 universe, full run: fetches history, computes indicators, calls
# Claude once per stock, validates + stores predictions, evaluates any
# previously-due predictions, and writes reports/YYYY-MM-DD.xlsx.

python -m src.run_daily --symbols RELIANCE.NS,TCS.NS
# Limits the universe to the given comma-separated symbols instead of the
# top 20 by weight — useful for dev/debugging without burning a full day's
# worth of Claude calls.

python -m src.run_daily --dry-run
# Runs the full pipeline, including real Claude calls, but writes nothing to
# SQLite or reports/ — prints/logs what would have been stored.
```

`--dry-run` and `--symbols` combine (`--dry-run --symbols RELIANCE.NS`) for
the cheapest possible test of a real end-to-end Claude call.

If invoked on a non-trading day (per `NseStaticHolidayCalendar`), the run
logs that fact and exits cleanly (`main()` returns `0`) without touching
SQLite or writing an empty report.

Each symbol is processed independently inside `run_pipeline()`: a missing
market-data fetch or a Claude response that fails validation twice causes
that one symbol to be skipped (counted in `skipped`) while every other
symbol in the run still completes.

## 5. Universe methodology

The universe is a static, version-controlled table of NIFTY-50 symbols and
their approximate published index weights in `src/universe/nifty50_weights.py`
(`NIFTY50_WEIGHTS`, currently 25 symbols with a comment noting the source and
last-refreshed date). Each run takes the top 20 by weight via
`src.universe.selection.select_top_n()`, which is a deterministic sort — the
same weights file always produces the same top 20, in the same rank order.

This is approximate and manually refreshed — there is no live scraping of
index composition in Phase 1. To refresh it: edit the `NIFTY50_WEIGHTS` dict
in `src/universe/nifty50_weights.py` with updated published weights and
update the "last refreshed" comment, then just re-run the pipeline. Because
every run records the exact 20 symbols and weights it used that day into the
`universe_snapshots` table (via `selection.record_universe_snapshot()`),
historical reports remain reproducible even after the weights file is later
updated — there's no silent survivorship bias in past reports.

## 6. Trading calendar

Horizons are defined in **trading days**, not calendar days — a 5-trading-day
prediction is never evaluated by adding 5 calendar days. This is implemented
by the `TradingCalendar` ABC (`src/universe/trading_calendar.py`) with three
methods — `is_trading_day(date)`, `add_trading_days(date, n)`,
`trading_days_between(start, end)` — and its Phase 1 implementation,
`NseStaticHolidayCalendar`.

`NseStaticHolidayCalendar` treats a date as a trading day if it is a weekday
(Monday–Friday) **and** not in the static holiday list in
`src/universe/nse_holidays.py` (`NSE_HOLIDAYS`, a dict keyed by year). It is a
best-effort, manually maintained list — the file's own comment says to
refresh it every January from the official NSE holiday circular
(nseindia.com) and to verify it against that circular before relying on it
for anything beyond development/testing.

## 7. Indicators & technical score

`src/analysis/indicators.py::compute_indicators(df)` computes, from the
cached OHLCV history for a symbol:

- **SMA** — 5, 10, 20, and 50-period simple moving averages (`sma5`, `sma10`,
  `sma20`, `sma50`); `sma50` is `None` whenever there are fewer than 50 bars
  of history (no fabricated value).
- **RSI(14)** (`rsi14`) — Wilder-style average gain/loss ratio; pinned to 100
  when average loss is 0, and 50 when both average gain and loss are 0 (flat
  series), so it never divides by zero.
- **MACD** (`macd`, `macd_signal`, `macd_histogram`) — 12/26 EMA difference
  and its 9-period EMA signal line.
- **Bollinger Bands** (`bb_upper`, `bb_mid`, `bb_lower`) — 20-period SMA ± 2
  standard deviations.
- **Support/resistance** (`support`, `resistance`) — min low / max high over
  the trailing 20-bar window (recent swing highs/lows).
- **Rolling volatility** (`volatility_percent`) — 20-period rolling standard
  deviation of daily returns, as a percentage.
- **Momentum / rate of change** (`momentum_roc_percent`) — percent change
  over a trailing 10-bar window (0 if there isn't enough history yet).
- **Volume trend** (`volume_trend_percent`) — percent change between the
  average volume of the most recent 20 bars and the prior 20 bars (0 if
  there isn't enough history).
- **Trend direction** (`trend_direction`) — `"UP"` if the latest close is
  above `sma20`, else `"DOWN"`.

These raw values feed `src/analysis/technical_score.py::compute_technical_score()`,
a deterministic, pure function that combines a fixed subset of the above
into a single score in `[-100, 100]` using these exact weights
(`SCORE_WEIGHTS`):

| Component | Weight |
|---|---|
| Trend (`close` vs `sma20`/`sma50`) | 0.30 |
| RSI | 0.20 |
| MACD (line vs signal) | 0.20 |
| Bollinger position | 0.15 |
| Momentum (ROC) | 0.10 |
| Volume trend | 0.05 |

Each component is first converted to its own `[-100, 100]` signal (e.g. trend
is +100/-100 if `close > sma20 > sma50` / `close < sma20 < sma50`, otherwise a
clamped percentage distance of `close` from `sma20`; RSI signal is
`(50 - rsi) * 2` clamped; MACD signal is +100/-100 depending on whether the
MACD line is above or below its signal line; the Bollinger signal is derived
from where `close` sits between the bands; momentum and volume signals are
clamped scalings of their raw percentages), then the weighted sum is rounded
to 2 decimal places. This score plus the raw indicator dict is exactly what
gets sent to Claude — Claude never recomputes indicators itself.

## 8. Prediction contract

**One Claude API call per stock per day**, covering all four horizons (1d,
5d, 10d, 20d — all in trading days) in a single structured JSON response.
This is the cost-control measure: 20 calls/day for the full universe, never
80. The prompt (`src/prediction/engine.py::build_prompt()`) contains only the
symbol, current price, technical score, and the computed indicator dict —
never the raw price history.

Claude is instructed to return strict JSON in exactly this shape:

```json
{
  "current_price": 1450.0,
  "horizons": {
    "1d":  {"direction": "BULLISH|BEARISH|NEUTRAL", "target_price": number, "range_low": number, "range_high": number, "expected_move_percent": number, "risk_level": number, "confidence": number (0-100), "reasoning": "string", "key_risks": ["string", ...]},
    "5d":  { "...": "same shape" },
    "10d": { "...": "same shape" },
    "20d": { "...": "same shape" }
  }
}
```

`src/prediction/engine.py::validate_response()` enforces, before anything is
stored:

- The response parses as JSON and is an object with `current_price` and
  `horizons` keys.
- `current_price` is numeric and matches (within 1% or 0.5, whichever is
  larger) the price the application actually sent — this is a sanity-check
  echo only; Claude's number is never trusted as authoritative, and Claude is
  never asked to look up or guess a price.
- All four horizon keys (`1d`, `5d`, `10d`, `20d`) are present, each an
  object with every required field (`direction`, `target_price`, `range_low`,
  `range_high`, `expected_move_percent`, `risk_level`, `confidence`,
  `reasoning`, `key_risks`).
- `direction` is one of `BULLISH`/`BEARISH`/`NEUTRAL`.
- `range_low <= range_high`.
- `confidence` is numeric and in `[0, 100]`.
- `key_risks` is a non-empty list of strings.

`request_prediction()` calls Claude, then validates. If the API call itself
raises (network error, API error, etc.) or the response fails validation, it
is logged and treated as one failed attempt — never a crash — and the
function retries once more. If the second attempt also fails (API error or
validation error), the stock is **skipped entirely for every horizon** (no
partial storage) and the run continues with the rest of the universe.

## 9. Storage schema

`src/storage/db.py` is the **only** module in the codebase that writes SQL —
every other module builds plain dicts/tuples and calls into `db` to persist
them. All four tables are append-only in normal operation; the application
never issues `UPDATE` or `DELETE` against them.

- **`universe_snapshots`** — one row per symbol per run date: `id,
  snapshot_date, symbol, index_weight, rank, source, created_at`. Preserves
  exactly which 20 symbols (and their weights) were used on a given day.
- **`price_bars`** — cached OHLCV, unique on `(symbol, date)`: `id, symbol,
  date, open, high, low, close, adj_close, volume, source, fetched_at`. A bar
  for a given symbol+date is inserted at most once (`INSERT OR IGNORE`).
- **`predictions`** — one row per stock × horizon, fully self-contained:
  `id, created_at, prediction_date, symbol, horizon_days,
  target_evaluation_date, current_price, direction, target_price, range_low,
  range_high, expected_move_percent, risk_level, confidence, reasoning,
  key_risks_json, technical_score, indicators_json, data_timestamp,
  data_provider, claude_model, prompt_version, raw_claude_response`.
  `target_evaluation_date` is computed once at creation time via
  `TradingCalendar.add_trading_days(prediction_date, horizon_days)` and never
  recomputed later.
- **`accuracy_evaluations`** — one row per evaluated prediction: `id,
  prediction_id, evaluated_at, evaluation_date, actual_close, actual_high,
  actual_low, window_high, window_low, direction_correct, target_hit,
  within_range, prediction_error, abs_error, pct_error,
  return_after_prediction_percent, max_favorable_excursion,
  max_adverse_excursion`.

## 10. Accuracy methodology

`src/accuracy/scorer.py::run_accuracy_evaluation()` runs at the start of each
pipeline run, before generating new predictions. It finds every prediction
whose `target_evaluation_date` has occurred and that has no matching row in
`accuracy_evaluations` yet (`find_predictions_due_for_evaluation`). For each,
`evaluate_prediction()` pulls the cached `price_bars` window for that symbol
from `prediction_date` (exclusive) through `target_evaluation_date`
(inclusive) and computes:

- `actual_close` / `actual_high` / `actual_low` — that single day's bar on
  `target_evaluation_date`.
- `window_high` / `window_low` — max high / min low across the whole window,
  used to check whether the price touched `target_price` at any point during
  the window, not only on the final day.
- `direction_correct` — whether the actual move (`actual_close -
  current_price`) matches the predicted `direction` (BULLISH ⇒ moved up,
  BEARISH ⇒ moved down, NEUTRAL ⇒ moved less than 0.5%).
- `target_hit` — for BULLISH, whether `window_high >= target_price`; for
  BEARISH, whether `window_low <= target_price`; for NEUTRAL, whether
  `target_price` fell within `[window_low, window_high]`.
- `within_range` — whether `actual_close` fell within `[range_low,
  range_high]`.
- `prediction_error` / `abs_error` / `pct_error` — `actual_close -
  target_price`, its absolute value, and that absolute value as a percent of
  `current_price`.
- `return_after_prediction_percent` — `(actual_close - current_price) /
  current_price * 100`.
- `max_favorable_excursion` / `max_adverse_excursion` — the best/worst price
  movement *in the direction predicted* during the window (e.g. for BULLISH,
  favorable is `window_high - current_price`, adverse is `current_price -
  window_low`).

If the price bar for `target_evaluation_date` isn't in `price_bars` yet (the
window is empty or doesn't end on that date), `evaluate_prediction()` returns
`None` and that prediction is simply left unevaluated until a future run
picks it up. **No look-ahead bias**: the evaluator only ever reads
`price_bars` rows that already exist as of "today", and a prediction is only
scored once its target date has actually occurred and its bar is cached —
never using data from after the evaluation date to grade an earlier one.

## 11. Excel report

`src/reporting/excel_report.py::generate_report()` builds `reports/YYYY-MM-DD.xlsx`
fresh on every non-dry-run invocation, reading only from SQLite (it never
writes to the database and the workbook is never hand-edited). It contains 8
sheets:

1. **Dashboard** — run date, universe size, predictions made/skipped that
   day, headline historical accuracy (direction accuracy %, target hit rate
   %, average error %) aggregated across all of `accuracy_evaluations`, and
   the disclaimer text.
2. **Today's Predictions** — every symbol × horizon generated on the run
   date.
3. **Prediction History** — the full historical log of every row ever
   written to `predictions`.
4. **Accuracy** — every `accuracy_evaluations` row joined with its parent
   prediction (symbol, horizon, predicted direction, confidence).
5. **Stock Performance** — accuracy metrics (direction accuracy %, target
   hit rate %, average % error, evaluation count) aggregated by symbol.
6. **Historical Prices** — cached OHLCV from `price_bars` for the current
   run's universe.
7. **News-Sentiment** — pre-defined, empty columns (`symbol, headline,
   sentiment_score, source, date`). The design spec calls this sheet
   "News/Sentiment (placeholder)"; it is written to the workbook as
   `News-Sentiment` because `/` is not a legal character in an Excel sheet
   name. It stays empty in Phase 1 — no sentiment data is invented.
8. **Configuration** — universe methodology, indicator/score formula version,
   prompt version, data provider name, generation timestamp, and the phase
   label (`Phase 1`).

## 12. Extending each provider interface

Every provider is consumed only through its abstract interface, injected by
`src/run_daily.py`. Adding a Phase 2 implementation never requires touching
`src/analysis/`, `src/prediction/`, `src/storage/`, or `src/reporting/`:

- **`MarketDataProvider`** (`src/providers/market_data.py`): implement
  `get_history(symbol, start, end) -> DataFrame | None` (columns `date, open,
  high, low, close, adj_close, volume`) and `get_latest_close(symbol) ->
  (date, price) | None` in a new file (e.g. `src/providers/kite.py`), then
  swap the `YFinanceProvider()` instantiation in `run_daily.main()` for the
  new class.
- **`FundamentalsProvider`** (`src/providers/fundamentals.py`): implement
  `get_fundamentals(symbol) -> dict` with real data in a new module, then
  wire it into `run_daily.py` wherever fundamentals are consumed (not
  consumed by the Phase 1 pipeline today — the interface and Phase 1 stub,
  `NotAvailableFundamentalsProvider`, exist purely so Phase 2 can slot in
  without a redesign).
- **`NewsSentimentProvider`** (`src/providers/news.py`): same pattern —
  implement `get_sentiment(symbol) -> dict`, replacing
  `NotAvailableNewsSentimentProvider`.
- **`TradingCalendar`** (`src/universe/trading_calendar.py`): implement
  `is_trading_day`, `add_trading_days`, `trading_days_between` against a
  more reliable holiday source, then swap `NseStaticHolidayCalendar()` for
  the new class wherever it's constructed (currently only in
  `run_daily.main()`).

In every case: write the new class implementing the ABC, then change the one
line in `run_daily.py` that instantiates it. The rest of the pipeline is
unaware of which concrete implementation it's talking to.

## 13. Known limitations

- **No automation** — Phase 1 is manual-execution only; there is no
  `launchd` (or cron/systemd) job installed. `run_daily.py` is written with
  proper exit codes and no interactive prompts so wiring in scheduling later
  is a small addition, not a redesign.
- **Static universe** — the top-20 selection is based on a manually
  maintained, approximate weights file (`src/universe/nifty50_weights.py`),
  not a live or dynamic (market-cap/liquidity based) selection.
- **No real fundamentals or news/sentiment data** — `FundamentalsProvider`
  and `NewsSentimentProvider` only have Phase 1 stubs that report "Not
  available in Phase 1"; nothing is estimated or invented in their place.
- **Single free data provider with no SLA** — `YFinanceProvider` wraps
  `yfinance` (an unofficial, free Yahoo Finance client). It retries transient
  failures a limited number of times and then skips the symbol; there's no
  paid/contracted data SLA behind it.
- **Manual holiday list maintenance** — `src/universe/nse_holidays.py` is a
  best-effort, manually maintained list that must be refreshed every January
  from the official NSE holiday circular; it is not sourced from a live
  calendar API/library in Phase 1.
